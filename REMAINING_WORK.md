### To unlock live preview (one manual step)

Reading **unpublished** content is an authenticated operation — this can't be worked around, by design (drafts are never public even in a dataset with public published content, which this project's is). Someone with access to the Sanity project needs to:

1. Go to **sanity.io/manage** → project `u0ztn8kn` → **API → Tokens → Add API token**.
2. Role: **Viewer** (read-only — the web app never writes to Sanity).
3. Put it in `apps/web/.env.local` as `SANITY_API_READ_TOKEN` (template: [apps/web/.env.local.example](apps/web/.env.local.example)).
4. Restart `npm run dev` in `apps/web`.
5. Open Studio → the new **Preview** tool in the left nav → click a page → click text → edit.

Nobody else can do this on your behalf — it requires an authenticated sanity.io session, which neither I nor a script can act on.

### ⚠️ The CSS-isolation gap (worth prioritizing)

The Custom HTML section is otherwise well-built — see [apps/studio/schemaTypes/sections/htmlValidation.ts](apps/studio/schemaTypes/sections/htmlValidation.ts) and [apps/web/src/lib/sanitizeHtml.ts](apps/web/src/lib/sanitizeHtml.ts), both allowlist-based, both deliberately let a `<style>` block through so an editor can style their own markup. The renderer wraps the output in `div.custom-html-section__inner` ([apps/web/src/components/PageSection.tsx:1906-1917](apps/web/src/components/PageSection.tsx#L1906-L1917)), and the code comment there says this makes it so the section "cannot style unrelated sections."

That's true for the wrapper's *own* rules (it scopes `img`/`table`/`video` sizing in [globals.css](apps/web/src/app/globals.css)), but it is **not** true for CSS the editor writes themselves. A plain `<style>` tag applies by DOM-wide selector matching, not by where it sits in the page — `<style>h2{color:gold}</style>` inside one section's Custom HTML block will restyle every `<h2>` on the entire site, including the header and other pages' content, not just that section. There's no Shadow DOM, `@scope`, iframe, or selector-rewriting anywhere in the pipeline to prevent that.

This matters because it's a promise made to the client in writing ("so other parts of the website aren't affected"), and right now it's false for a predictable, easy-to-trigger case — nothing exotic, just someone writing a selector without thinking about the whole site. Two ways to actually deliver on it, roughly in order of effort:

1. **Rewrite selectors at render time.** Parse each `<style>` block's CSS and prefix every selector with the section's own generated class (e.g. `.chs-a1b2c3 h2 { color: gold }`). Needs a small CSS parser (`postcss` + a rewriting plugin, or the modern `@scope` at-rule if the target browsers support it — `@scope (.chs-a1b2c3) { h2 { color: gold } }` is a one-line wrap, no parsing, but check the project's actual browser support bar before relying on it).
2. **Shadow DOM.** Render the section's HTML inside a `<div>` with `attachShadow({mode: 'open'})`. Real isolation (also stops the section's CSS from being affected by the rest of the site, which `@scope`/prefixing doesn't), at the cost of the section no longer inheriting the page's design tokens/fonts unless those are explicitly piped in via CSS custom properties (which this codebase already uses heavily for theming, so that's a solvable, maybe even natural, fit).

### Still to build

- **A reusable-section library.** Today, "reusable" in the code's own comments means "the same section type is available on every page schema" (a developer-level fact), not "an editor can save one configured section and drop it into other pages, then update every copy from one place." That second thing needs a new referenced document type (e.g. `sharedSection`) that pages reference instead of (or alongside) inline sections — a bigger schema change than it sounds, since `PageSection.tsx`'s rendering dispatch keys off `section._type`, and resolving a reference adds a query-time `->` dereference everywhere sections are fetched.
- **Page-specific CSS.** A `customCss` text field on `customPage` (and the other page types), sanitized the same way the HTML section's `<style>` blocks already are, then rendered once near the top of that page — straightforward once a decision is made on how it should be scoped (page-wide is what's promised, so unlike the section case above, "no scoping" might be the intended behavior here — worth confirming with the client's actual use case, e.g. "override all my button colors on just this page").
